## Deviations from the brief (all verified against the installed 2.5.3 binary)

1. **`"rules": { "recommended": true }` → `"rules": { "preset": "recommended" }`.**
   The former is deprecated in 2.5.3 ("will be removed in the next major
   version... Use preset instead"). I empirically verified `preset:
   "recommended"` produces identical diagnostics to `recommended: true` on a
   test file (3 errors, 1 warning both ways), while `biome migrate`'s own
   suggestion of `preset: "none"` **silently disables all recommended rules**
   (same file dropped to 1 error) — that would have been a real strictness
   regression against constraint 2, not a mechanical rename. Went with the
   non-deprecated equivalent that behaves identically.
2. **Enabled `useComponentExportOnlyModules`** (style group, stable since
   1.9.2 — not nursery, so this doesn't violate constraint 2). The brief
   asked me to enable it if stable and it is. Added
   `allowConstantExport: true` to mirror the old
   `reactRefresh.configs.vite` preset's default option. It flagged exactly
   the two files (`badge.tsx`, `button.tsx`) that already carried an
   `eslint-disable-next-line react-refresh/only-export-components` comment
   — i.e. this is carrying forward an existing, already-reviewed
   suppression, not introducing a new one.
3. **Added `css.parser.tailwindDirectives: true`.** Without it, Biome's CSS
   parser cannot parse `src/index.css`'s `@theme inline { ... }` block
   (Tailwind v4 syntax) at all — `npx biome check` reported a hard parse
   error ("Tailwind-specific syntax is disabled"), which would have broken
   both linting and the one-time reformat for that file. Confirmed the key
   name against the 2.5.3 JSON schema (`CssParserConfiguration.tailwindDirectives`,
   "Enables parsing of Tailwind CSS 4.0 directives and functions").
4. **Added `coverage` to `.gitignore`.** The brief's own rationale text says
   `dist`/`coverage`/`*.tsbuildinfo`/`node_modules` "are excluded via
   `useIgnoreFile` (.gitignore)" — but `.gitignore` did not actually list
   `coverage` (only `dist`/`dist-ssr`/`node_modules`). One-line fix so that
   stated intent is actually true; `coverage/` doesn't exist in the tree
   today so this has zero effect on `npm run ci`, it only prevents a future
   `npm run coverage` run from getting its generated report files linted.

## New diagnostics Biome's recommended rules surfaced (ESLint never flagged these — confirmed by a clean baseline `npm run ci` before touching any tooling)

Two were genuinely mechanical, fixed directly (not suppressed):
- `lint/a11y/useButtonType` × 2 (`AlgorithmSelector.tsx`, `Visualizer.tsx`)
  — added `type="button"` to two non-form buttons.

The rest are targeted `// biome-ignore <rule>: <reason>` suppressions (all
listed here per Global Constraint 5), grouped by rule:

- **`lint/correctness/useExhaustiveDependencies`** (9 sites: 8 in
  `useAlgorithmPlayer.ts`, 1 in `useSound.ts`). `stopInterval`,
  `startInterval`, `advance` (useAlgorithmPlayer.ts) and `getCtx`
  (useSound.ts) are plain functions that close over refs and are stable in
  *behavior* across renders without being wrapped in `useCallback`; several
  effects are also deliberately scoped narrower than their full closure
  (mount-only, speed-change-only) — adding the "missing" deps would change
  runtime behavior (e.g. an effect meant to run only on `algorithmId`
  change would re-run every render). 4 of these 9 sites replace a stale,
  now-inert `// eslint-disable-next-line react-hooks/exhaustive-deps`
  comment that predates this migration; the other 5 are genuinely new
  findings — Biome's implementation is stricter here than
  `eslint-plugin-react-hooks` was for this file. I did not rewrite the hook
  logic: that's a real refactor (thread stable callbacks through
  `useCallback`/`useRef` everywhere) outside a lint-tool-swap task's scope,
  with behavior-change risk I can't fully verify without deeper testing.
- **`lint/style/noNonNullAssertion`** × 3 (`main.tsx`,
  `Visualizer.tsx`, `useAlgorithmPlayer.ts`). Not in old
  `typescript-eslint` "recommended" (non-type-checked) — confirmed by the
  clean baseline. Each `!` is guarded by adjacent logic (root element
  guaranteed by `index.html`, `'bubble-sort'` is a registered algorithm id,
  `historyRef.current.length <= 1` check before `.at(-1)!`).
- **`lint/a11y/useSemanticElements`** × 1 (`Controls.tsx`, `role="group"`
  div). Suggested fix is `<fieldset>`, which carries UA default
  border/padding that would need a CSS reset — visual-regression risk I
  didn't want to take in a tooling-migration task.
- **`lint/a11y/noLabelWithoutControl`** × 2 (`Controls.tsx`, the Speed and
  Array size sliders). Biome can't see that `<Slider>` (Radix) renders its
  own accessible control with its own `aria-label` — the wrapping
  `<label>` is a visual grouping only.
- **`lint/a11y/useAriaPropsSupportedByRole`** × 2
  (`StepCodeWalkthrough.tsx`, `Visualizer.tsx`). Per the ARIA spec, a plain
  `<div>`'s implicit `role="generic"` doesn't formally support
  `aria-label`; these are static labeled regions, not interactive content,
  and jsx-a11y's older/looser rule never caught this.
- **`lint/suspicious/noArrayIndexKey`** × 1 (`StepCodeWalkthrough.tsx`).
  The mapped `lines` array is a static per-`algorithmId` constant
  (`PSEUDOCODE[algorithmId]`), never reordered/inserted/removed while
  mounted — index-as-key is safe here (this is a different array from the
  animated `SortBars`, which already correctly uses `entry.id` per
  CLAUDE.md convention).
- **`lint/a11y/noSvgWithoutTitle`** × 3 (`public/favicon.svg`,
  `public/apple-touch-icon.svg`, `public/icons.svg`). New coverage —
  ESLint's jsx-a11y only lints JSX, never touched these standalone SVG
  files. None of the three is ever inserted into the page DOM
  (favicon/touch-icon are referenced only via `<link>`; `icons.svg` is a
  `<symbol>` sprite sheet consumed via `<use>`), so a `<title>` on the
  wrapper `<svg>` would have zero accessibility value — suppressed with
  reason instead of adding a meaningless element.
